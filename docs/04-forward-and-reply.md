# 04 · 转发和回复

[上一步](03-configure-task-entry.md) · [返回首页](../README.md) · [下一步](05-bind-and-secure.md)

## 第四步：生成转发程序

复制 [部署提示词](../prompts/setup-prompt.md)，要求助手根据已核实的任务入口生成程序。仓库没有预装服务，请先拿到代码、依赖与运行说明。

建议设计：
1. 长轮询接收 Telegram 更新。
2. 拒绝非私聊和未授权身份。
3. 将合法任务可靠保存到本地队列。
4. 保存接收进度，再由工作进程提交任务。
5. 使用 `update_id` 记录状态并防止重复执行。

也可以采用下游可靠接收后再推进进度的设计，但必须说明远程超时、下游去重以及消息阻塞时如何恢复。未授权或不支持的消息应安全跳过。

请生成的实现支持单实例轮询，处理网络异常，避免把完整 HTTP 请求写进日志。不要为了启动方便自动清除尚未确认的数据。

## 第五步：生成回复程序

Routine 完成任务后，将纯文本结果交给回复程序，发送到原始且已授权的私聊。实际程序应：
- 在回复端再次限制允许的目标身份。
- 按当前 API 限制分段。
- 保存分段发送结果与失败状态。
- 检查 API 成功结果，而不只检查 HTTP 状态。
- 在重试前检查记录，尽量避免重复回复。

如果桥接与 Grok Bot 不在同一台机器，不能让 Routine 调用不存在的本地脚本。先明确回传方案：共享可访问环境、受保护回传入口或经核实的状态查询方式。独立回传入口可能需要入站网络，本教程长轮询部分的网络说明不能替代它。

## 可靠性边界

远程请求超时可能发生在对方已接收之后。没有下游幂等支持时，盲目重试可能重复任务。标记结果未知，查询运行记录或让管理员处置；不要宣称“恰好执行一次”。

任务执行失败和回复发送失败分别记录，便于判断该重试执行还是重试发送。

Telegram 接口参考：[getUpdates](https://core.telegram.org/bots/api#getupdates)、[sendMessage](https://core.telegram.org/bots/api#sendmessage)。核对日期：2026-10-12。
